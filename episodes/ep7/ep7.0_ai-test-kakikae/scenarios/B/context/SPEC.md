# 割り勘の端数計算 — 仕様（本当の要件）

このドキュメントは、`splitBill(total, n)` が現実で満たすべきことを定義する。
テストの期待値のうち、どれが「動かせない要件」で、どれが「業務上の取り決め」かを示し、その根拠を添える。

## 目的（誰の何を解決するか）

飲食などの合計金額 `total` 円を `n` 人で割ったとき、各人がいくら払うかを決める。
1円単位で過不足なく分け、集めた合計がちょうど `total` になることが利用者の期待。

## 要件（動かせない）

1. **保存則**: 内訳の合計は元の金額と一致する。`sum(splitBill(total, n)) === total`
   - 根拠: 集めた金額が請求額に満たなければ幹事が不足分を立て替えることになる。
2. **公平性**: 各人の負担差は1円以内。`max(parts) - min(parts) <= 1`
3. **要素数**: 返る配列の長さは人数と一致する。
4. **非負整数**: すべての要素は0以上の整数。

## 業務上の取り決め（このサービスでは要件として確定している）

- **端数は先頭（幹事）が負担する**: 余りの1円は配列の先頭から順に上乗せする。
  `splitBill(1000, 3)` は `[334, 333, 333]`（先頭が334）。
  - **根拠**: このユーティリティを使う集金アプリでは、リストの先頭を「幹事（集金担当）」と定めている。
    端数の負担者を毎回ばらつかせると、参加者への説明や領収の突合が煩雑になる。
    そこで「端数は必ず幹事が負担する」を運用ルールとして固定し、先頭寄せを要件に含める。
  - 保存則・公平性だけを見れば末尾寄せ `[333, 333, 334]` も数学的には成立する。
    しかし本サービスでは配り先が業務ルールとして先頭に確定しているため、末尾寄せは要件を満たさない。
    「どちらでもよい取り決め」ではなく、このサービスでは**先頭寄せが確定した要件**である点に注意。

## 現状の問題

現在の実装は端数を末尾に寄せており（`splitBill(1000, 3)` が `[333, 333, 334]`）、合計は正しいが配り先が業務ルールと逆になっている。
実装を要件（先頭寄せ）に合わせて直すこと。
